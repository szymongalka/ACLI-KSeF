# ACLI-KSeF boundaries

- Choose the credential path approved for the profile. The direct ASEF CLI accepts a system keyring or protected systemd credential on the Gateway host. If the owner selects OpenClaw Secret Store, a saved SecretRef is not a CLI login: the HTTPS egress proxy substitutes it only at request time, while ASEF must RSA-encrypt the token first. Use only an approved SecretRef-aware integration that resolves the token before encryption; verify its actual login before claiming access. Do not extract the store value or silently move it into another credential store. A KSeF certificate is a separate `.crt` plus encrypted `.key` pair; keep its password in the selected supported credential path. Never request tokens, private key contents, archive passwords, or private key passwords in chat; never print them or place them in project files or command arguments.
- `registry check` needs no key. It automatically checks the MF VAT register and KRS when a KRS number is available. Its CEIDG and GUS links are for manual checks; do not present MF data as a direct CEIDG or GUS verification. Report the source and check time.
- `asef vat rates` gives a general current rate catalog and source. It does not determine the correct rate for a particular sale; ask the user or rely on a verified classification/WIS when needed.
- If KSeF returns an uncertain submission result, preserve the reference and check status before any retry. Do not resend a document merely because status is pending.
- Register an existing KSeF certificate pair explicitly with `asef auth add-certificate CERT KEY --purpose Authentication` or `--purpose Offline`, then inspect `asef auth certificates` for its fingerprint. The key must be encrypted PEM PKCS#8. Registration checks the pair and keeps the original encrypted `.key` in the private ASEF data directory; its own password is requested in a hidden local prompt but is not retained during registration. `Offline` certificates cannot authenticate to KSeF. ASEF does not scan the filesystem for certificates.
- On a host using the system keyring, select a registered `Authentication` certificate for the intended profile with `asef auth use-certificate FINGERPRINT --nip NIP --env ENV`. `--subject-identifier` accepts `certificateSubject` or `certificateFingerprint` when that choice is needed. The hidden local prompt saves the `.key` password to the keyring for later KSeF logins. Use `asef auth use-token --nip NIP --env ENV` to switch the profile back only when a token is available, then `asef auth check --nip NIP --env ENV` to test the selected login. Do not select a certificate for another profile by guesswork.
- On a systemd Gateway with `CREDENTIALS_DIRECTORY`, select exactly one protected credential for each profile: `asef_<env>_<nip>` for a token, or `asef_cert_<env>_<nip>` for certificate login. The latter is JSON with `fingerprint`, `password`, and `subjectIdentifierType` (`certificateSubject` or `certificateFingerprint`); it points to a registered `Authentication` certificate. If both files exist, ASEF rejects the ambiguity; it does not fall back to the keyring. Provision these credentials outside chat and the repository.
- For migration, `asef db export PATH` encrypts the full SQLite database, available KSeF tokens, and explicitly registered certificate/key pairs with a password entered in a hidden CLI prompt (at least 12 characters on export). Check the reported certificate count and profiles without tokens. `asef db import PATH` restores into a fresh `ASEF_DATA_DIR`, keeping certificate files under its private `certificates` directory, and a working keyring with no token collisions. The archive contains original encrypted `.key` bytes, but neither their passwords nor the keyring's certificate selections. After import, reselect/provision the login method and run `auth check` before network work; `use-token` requires a token for that profile. If `CREDENTIALS_DIRECTORY` is set, importing an archive with tokens fails before database restore; provision systemd credentials separately. `asef db backup PATH` is a private, unencrypted SQLite copy without tokens or certificates. Never put any export in the repository.
- To transfer invoices without full database state or KSeF credentials, use password-protected `asef invoice export-bundle PATH` and `asef invoice import-bundle PATH`; export accepts `--nip` and `--env`. XML bundles exclude tokens, certificates, and private keys. XML bundle import can add to an existing database, skips identical XML, and resets send approvals. Review and approve an imported draft before sending.
- In OpenClaw, ASEF runs on the Gateway host. A preview path belongs to that host; attach the PDF or HTML to the operator's conversation before asking for consent. If the preview cannot be shown, do not approve or send. Use the Gateway's ASEF database and credential store, not a separate Mac checkout.
